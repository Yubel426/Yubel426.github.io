Motivation

Can a coding agent watch a video of a physical event and then reproduce that event, physically correctly, in a simulator? Physically correct means more than a matching picture: the scene needs the right objects, shapes, masses, contacts and initial state, under one fixed set of physical laws, so that it runs on its own and the same scene can also answer what would happen if the ball were heavier or the ramp steeper.

We gave Codex a MuJoCo environment and asked it to reconstruct simulated and real videos. It delivered a scene every time, and its renders often look close to the source. When we read the delivered scenes and the scripts behind them, three problems kept coming back.

01

No precise geometry. It cannot count or measure what the video shows.

02

Invented parts. To reproduce the motion, it adds mechanisms the real scene does not have.

03

No evidence loop, no acceptance test. Nothing tells it which candidate is better or when to stop, so the search runs on.

  • Error 1 · No precise geometry. With only a vision-language model looking at frames, Codex cannot recover exact geometry: one ramp holds 14 dominoes in the video and 21 in its scene.
  • Error 2 · Invented hinges. Codex reproduces the motion and the appearance, but only by adding parts the scene does not have: every domino in its scene turns on a hinge.

Method

The harness takes the agent from a video to a delivered scene in five stages. The agent owns the physical hypotheses. The harness owns the observations, the rules and the grading.

  • Observe. A VLM inventories the scene, SAM3 tracks each object, Pi3X recovers depth and the camera, and each object gets a primitive or mesh geometry and an initial state.
  • Hypothesize. The agent edits scene.json, declares the physical processes it expects, and states what the change should improve.
  • Fit. In a sandbox with MuJoCo, the agent writes its own optimizer over exact local rollouts of the same integrator the evaluation uses.
  • Evaluate. The harness compiles the candidate, runs it once over the whole video, renders it from the source camera and compares it with the SAM3 tracks. Feedback names the earliest window where it diverges, and when the candidate becomes the new best, an independent VLM review of its renders joins the feedback.
  • Deliver. The most accurate evaluated candidate is delivered with its evidence, open questions and full history.

The two loops are the core of the design. The inner loop is cheap and private: the agent can try any parameter search it likes. The outer loop is expensive and public: every candidate the agent submits is rerun from scratch by code the agent cannot touch, and only those results decide what gets delivered.

Results

We ran Plumb and Codex alone on the same 29 videos, drawn at random within each category: two per category from Physion v1.5 and three per category from PhysInOne. Codex gets the video and a MuJoCo environment, with no harness and no token limit. Plumb ran three times on the current code from the same initialization (scene inventory, SAM3 tracks, Pi3X), counted once per video in the tokens below. The three runs differ only in how much discovery the token budget allows: about 2, 3 or 4 official evaluation rounds per video.

Both datasets play slower than real time, so we retimed their videos to real-time speed before this comparison.

An external evaluator reruns each delivered scene as a passive rollout and scores it against dataset ground truth, counting only objects that actually move and only the frames where they are visible. Mask IoU and 2D trajectory error (ADE, in pixels) come from Physion and PhysInOne instance masks. 3D ADE uses ground-truth trajectories after a similarity alignment at frame 0. Neither system reads ground truth.

Agentic tool use

Each tool replaces something the agent would otherwise do by eye or by hand.

Runtime: any model, persistent sessions, recoverable runs

Plumb is not tied to one model. Every role, from scene understanding to proposals and review, can run on any vision-capable model on the market, from OpenAI, Anthropic, Google, xAI, DeepSeek, Qwen and many other providers, chosen at launch. This comes from Pi, an open-source toolkit for coding agents that combines one LLM interface across dozens of providers with an agent runtime.

Pi also manages each conversation: message history, tool calls, retries, context compaction and session recovery. Plumb only adds task inputs, experiment results and tool outputs. The proposal agent keeps one conversation per branch, while each reviewer starts a fresh session. Every stage writes a checkpoint, so an interrupted run resumes where it stopped, and a finished run can later be refined from its delivered scene.

Scene understanding: what is there, and where it is in every frame

A vision-language model (VLM) reads a storyboard of the video and writes a scene graph. Each node is one body that moves as a single piece, annotated with its role in the event (moving, support or obstacle), its visibility and how it should be represented. An object stays in the inventory even while it is occluded.

Each node becomes a short text prompt for SAM3, which returns masks tracked through the video; the VLM then reviews the candidate tracks and assigns identities. Without this step, the agent measures objects with color thresholds and hand-typed pixel coordinates.

Depth and camera estimation: lifting the video into 3D

Pi3X estimates per-frame depth, camera intrinsics and camera poses. With them, each mask is lifted into 3D, all objects share one metric frame, and every candidate is rendered from the recovered source camera, so it is compared with the video in the same image plane.

Geometry: primitives for simple objects, meshes for complex ones

A simple object gets a primitive chosen by the VLM (a sphere, box, cylinder, capsule or open container), sized per axis from its lifted masks. It collides as exactly that shape, which keeps contacts stable and masses meaningful. A complex object gets a mesh reconstructed by SAM3D from a reviewed reference frame.

The ground, or whatever surface supports the objects, is fitted as a plane to the estimated depth with RANSAC. Its normal defines the direction of gravity.

Process plan and proposals: state the hypothesis before the test

Before submitting a scene, the agent declares the physical processes it expects (free motion, sustained contact, collision or constrained motion), together with the objects involved, the time windows in which they move and the contact events. The plan persists across rounds and is checked against the simulated rollout.

Each submission is a small scientific claim: a problem statement, a hypothesis, the parameters the change may touch, and measurable targets written before the result exists, for example that an object's trajectory error decreases while its coverage does not. The harness verifies that nothing outside the declared scope changed, then freezes the submission.

A lower error alone does not confirm a hypothesis. Feedback reports passed targets, metric changes and unresolved issues separately.

Local fitting: the agent writes its own optimizer

A coding agent's main advantage is speed: it can run thousands of simulations inside an optimization loop. Plumb keeps that advantage. In an isolated sandbox without network access, the agent has MuJoCo and a fitting library whose rollouts match the official evaluation exactly. It declares which parameters may change, including a single global scale, fits them to the SAM3 masks with any optimizer it chooses, checks the result against the official motion and event checks, and attaches a fitting report to the submission.

Evaluation: one rollout over the whole video, outside the agent's reach

Each submitted candidate is simulated once from t = 0 over the entire video, rendered from the recovered camera and compared with the SAM3 tracks. The comparison reports per-object trajectory error (ADE, relative to the image diagonal), mask IoU, and how much of each observed object the prediction covers.

Acceptance checks cover every observed motion window of every object, whatever processes the agent declared, as well as each declared event and the initial state. Feedback names the earliest window where simulation and video diverge. When the comparison itself fails, the run stops at a checkpoint instead of asking the agent to change the physics.

When a candidate becomes the new best, an independent VLM reviewer, in a fresh session with no access to the agent's reasoning, compares its renders with the source frames. The review runs during discovery, so its findings reach the next proposal rather than arriving after the run ends.

Delivery: reproducible first, then accurate, then certified

Candidates are ranked in three tiers. A candidate must first be reproduced by a plain fixed-timestep replay from its initial state. Accuracy comes next: trajectory error and mask IoU over the moving objects, with the primary object weighted twice and each measure judged against its own noise band. A candidate wins when one measure improves and the other does not regress; a trade-off goes to the larger relative change, and a candidate that covers less of an observed object cannot win. Only at equal accuracy do the review verdict and failed checks decide.

Stopping follows a rule as well. The agent may conclude only after two consecutive evaluations fail to improve the best candidate by 10%, or when less than 15% of the token budget remains, and not while a revision requested by the reviewer is still unaddressed. If the agent picks a round that is measurably worse than the best one, the best is delivered and the agent's choice is recorded.

What's next

  • More 3D foundation models. Plumb shows that 3D tools are what let a coding agent measure a scene instead of guessing it. Next we will add more 3D tools built on foundation models, for example 3D trackers and object pose estimators, and compare the evidence each one adds.
  • Richer evidence. Mask IoU and trajectory error alone are not precise enough to judge a reconstruction. More tools would give every round more varied evidence to iterate on.
  • 3D tools built for agents. SAM3 tracking makes initialization slow. We want to study 3D tools that suit an agent better, for example one that returns a quick, coarse scene initialization without chasing precision and leaves the refinement to the agent's own loop.
  • Harder scenes. Plumb is currently limited to rigid-body motion. We want to take it to harder scenes, such as deformable objects, cloth and fluids.
